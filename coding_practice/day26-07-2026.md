## ELK Stack — Short & Simple Notes

Based on your 13-page PDF, here is the **short version without removing important concepts**. 

### 1. What is ELK?

**ELK = Elasticsearch + Logstash + Kibana**

Used mainly to **collect, process, store, search and visualize logs**.

**Flow:**

```text
Application / Server / System
          ↓
       Logstash
   Collect + Parse + Filter
          ↓
    Elasticsearch
   Store + Index + Search
          ↓
        Kibana
  Search + Dashboard + Visualize
```

---

## 2. Log Parsing

**Parsing = raw log ko useful structured data mein convert karna.**

Example:

```text
2025-05-01 12:31:02 [ERROR] Failed to connect to database
```

Parse karke:

```text
timestamp = 12:31:02
level     = ERROR
message   = Failed to connect to database
```

This makes logs easier to **search, analyze and troubleshoot**. 

---

# 3. Elasticsearch

### What?

A **distributed search and analytics engine**.

### Main job:

**Store + Index + Search data quickly.**

Data is stored as:

```text
Index
  ↓
Documents
  ↓
JSON
```

Example:

```json
{
  "timestamp": "...",
  "level": "ERROR",
  "message": "DB connection failed"
}
```

### Important concepts

* **Index** → collection of documents
* **Document** → JSON data/log record
* **Shard** → index ka partition
* **Replica** → shard ki copy
* **Node** → Elasticsearch server

Elasticsearch uses **shards and replicas** for scalability and fault tolerance.

# 4. Logstash

### What?

A **data processing pipeline**.

### Main job:

```text
Input → Filter → Output
```

### Input

Logs can come from:

* Files
* Applications
* Databases
* HTTP
* Syslog
* External systems

### Filter

* Parse logs
* Extract fields
* Transform data
* Enrich data

Common filters:

* **Grok**
* **Date**
* **GeoIP**

### Output

Usually:

```text
Logstash → Elasticsearch
```



---

# 5. Kibana

### What?

A **web UI for Elasticsearch data**.

### Main job:

**Search + Explore + Visualize**

You can create:

* Dashboards
* Charts
* Graphs
* Tables
* Maps
* Real-time views

Example:

```text
Elasticsearch
      ↓
    Kibana
      ↓
Dashboard
```

Kibana itself is **not the main storage**; it visualizes data stored in Elasticsearch.

# 6. Complete ELK Working

### Step 1 — Collect

Logstash collects raw logs.

```text
Application → Logstash
```

### Step 2 — Process

Logstash parses and structures them.

```text
Raw Log
   ↓
Grok / Filters
   ↓
Structured Data
```

### Step 3 — Store

Logstash sends data to Elasticsearch.

```text
Logstash → Elasticsearch
```

Elasticsearch indexes and stores it.

### Step 4 — Visualize

Kibana reads Elasticsearch data.

```text
Elasticsearch → Kibana → Dashboard
```

# 8. Elasticsearch Shards & Replicas

### Primary Shard

Original partition of data.

### Replica Shard

Copy of primary shard.

### Node

Server running Elasticsearch.

### Formula

**Total Shards:**

```text
P × (R + 1)
```

Where:

* `P` = Primary shards
* `R` = Replicas per primary

Example:

```text
P = 5
R = 1

5 × (1 + 1) = 10

5 Primary + 5 Replica
```



---

# 9. Minimum Nodes

Formula:

```text
Minimum Nodes = R + 1
```

Why?

A replica **cannot be placed on the same node as its primary**.

Example:

```text
R = 2

Minimum nodes = 2 + 1 = 3
```

### Failure tolerance

```text
Maximum node failures = R
```

So:

```text
R = 1 → 1 node failure
R = 2 → 2 node failures
```



---

# 10. Shard Sizing

Recommended shard size:

```text
10–50 GB
```

Formula:

```text
Primary Shards =
Total Data Size ÷ Target Shard Size
```

Example:

```text
Data = 500 GB
Shard size = 25 GB

500 ÷ 25 = 20 primary shards
```

If replicas = 1:

```text
20 × (1 + 1) = 40 total shards
```

### Remember

**Too many shards** → memory overhead

**Too few shards** → poor parallelism

**Replicas improve:**

* Availability
* Read performance

**Replicas do NOT improve write performance.**

# 11. ILM — Index Lifecycle Management

**ILM = automatically manage Elasticsearch indices as they become old.**

Mainly useful for:

* Logs
* Metrics
* Time-series data
* Security events

### Why ILM?

Without ILM:

```text
Indices keep growing
       ↓
Storage increases
       ↓
Performance decreases
       ↓
Manual cleanup required
```

ILM automatically handles:

* Rollover
* Shrinking
* Moving data to cheaper storage
* Deleting old data



---

# 12. ILM Phases

Think of log data becoming older:

```text
HOT → WARM → COLD → FROZEN → DELETE
```

### 🔥 Hot

* Current data
* Frequently written/read
* High-performance storage
* Full replicas

Example: **current logs**

### 🌤 Warm

* Read-only
* Less frequently accessed
* Can reduce replicas/shards

Example: **last month's logs**

### ❄ Cold

* Rarely accessed
* Cheap storage
* Slower search

### 🧊 Frozen

* Very rarely accessed
* Minimal resources
* Optional

### 🗑 Delete

* Automatically delete old data
* Free storage



---

# 13. Rollover

Rollover creates a **new index when size or age limit is reached**.

Example:

```text
max_size = 50GB
max_age  = 7 days
```

Whichever happens first:

```text
50GB reached OR 7 days reached
             ↓
       New index created
```

Example naming:

```text
logs-000001
logs-000002
logs-000003
```



---

# 14. Example ILM Policy

Suppose:

```text
Rollover → 50GB or 7 days
Warm     → after 30 days
Delete   → after 90 days
```

Then:

```text
0–30 days   → Hot
30–90 days  → Warm
90+ days    → Delete
```

This happens automatically. 

---

# 15. Important Best Practices

### Elasticsearch

* Keep shard size around **10–50 GB**
* Avoid too many small shards
* Use replicas for availability
* Monitor cluster health
* Use ILM for old data
* Delete unnecessary old logs

### ILM

```text
Hot → Warm → Cold → Frozen → Delete
```

Main goal:

**Balance Performance + Availability + Cost**.
